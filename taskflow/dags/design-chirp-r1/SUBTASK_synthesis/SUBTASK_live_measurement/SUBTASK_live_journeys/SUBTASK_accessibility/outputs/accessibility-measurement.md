# Accessibility cluster — live measurement (`manual_user_check`)

**Cluster**: keyboard & screen-reader path, WCAG checks · **Owned criteria**: 18 (`BAR-031`, `BAR-218`, `BAR-276`–`BAR-284`, `BAR-286`–`BAR-292`)

## Access note

The live `Nousix-LLC/nswe-demo` **chirp** product was reached and exercised read-only. The deployed
revision is a descendant of `c805525` whose only intervening commits are documentation, design, and
deploy-path hygiene — no product-code change — so the running product realizes `c805525`'s code. The
UI is a client-side WebAssembly single-page app (`crates/chirp-frontend`, served as `pkg/chirp.js` +
`pkg/chirp_bg.wasm`) mounted into `<div id="app">`; the rendered DOM a keyboard and screen reader
encounter is produced entirely by that Rust source, so accessibility affordances (roles, labels,
landmarks, headings, live regions, focus handling) were measured against the SPA source at `c805525`
together with the live served shell and the live API. The served HTML shell declares `<html lang="en">`
and a zoomable viewport (`width=device-width, initial-scale=1`, no `maximum-scale`/`user-scalable=no`),
with a single inline 20-line stylesheet. Checks that strictly need a rendered screen-reader session are
judged conservatively from the source that determines them, with the basis stated. The verdicts below
reference the product only by repository identity, commit SHA, and repo-relative path.

## Verdict table

| BAR-031 | partial | Core-loop reading and the authored controls are largely accessible, but the loop cannot be completed by keyboard + screen reader end to end. In `crates/chirp-frontend/src`: compose/post (`compose.rs`) uses `<label for>`-associated `<input>`/`<textarea>` and a native `<button>`; the timeline (`timeline.rs`) renders a `<ul>`/`<li>` feed under an `<h1>`; follow is a native `<button>` (`profile.rs`). But the persistent nav (`app.rs` `nav_bar`) uses the router's `<span role="link" tabindex="0">` with a **Click-only** handler (`ferric-router/src/link.rs`) — Enter/Space do not activate it — so a keyboard user cannot move between Timeline and Compose; there is no reply control and no interactive like control in the timeline (likes render as a text span), and no keyboard-reachable link from the timeline to a profile. Names/roles are exposed on the controls that exist; loop completion is blocked. |
| BAR-218 | met | No stylesheet in the product suppresses the focus indicator: the only CSS is the shell's 20-line inline block (body font, nav margin, link colour) with no `outline:none` and no `:focus` override, and every focusable control is a native `<button>`/`<input>`/`<textarea>` or the router `<span tabindex="0">`, all of which carry the user agent's default focus ring on the white background. No focusable control takes focus without a visible indicator. Verdict grounded in the complete served CSS plus the control markup at `c805525`; a rendered pass would confirm the default ring but nothing in source removes or weakens it. |
| BAR-276 | missing | Keyboard-only operation of the full action set fails. The nav links (`app.rs` via `ferric-router/src/link.rs`) are `<span role="link">` with a Click-only handler, so navigation itself is effectively pointer-only — directly contrary to "no action is reachable by pointer only." There is no reply control, no "more" control, and no interactive like control on the timeline; profiles (`/user/:id`) have no keyboard-reachable link; and no settings sub-section exists in the build (`app.rs` route table is `/`, `/compose`, `/user/:id`, fallback). A keyboard-only user cannot complete sign-in-via-nav, open a profile, operate reply/like/more, or reach settings. |
| BAR-277 | partial | Within a screen, tab order follows DOM reading order (no `tabindex` reordering beyond the router span's `0`) and the UA focus indicator is present, so timeline and the compose/login form tab in reading order. In-screen focus order holds; route-change focus landing is unimplemented. |
| BAR-278 | partial | No screen traps keyboard focus with no way out: there is no focus-trap code and no modal dialog anywhere in `crates/chirp-frontend`, so focus is never stuck. The specified modal focus management (a dialog holding focus, cycling on Tab, closing on Esc/Cancel, and returning focus to the opener) is absent because compose is a full route rather than a modal and there is no destructive-confirmation dialog. The "no stuck focus" guarantee holds; the modal machinery a releasable build would need is not present. |
| BAR-279 | missing | No "Skip to content" control exists (the only elements before the outlet are the two nav links in `app.rs` `nav_bar`), and no `<main>` landmark is rendered anywhere in `crates/chirp-frontend` (views wrap content in `<section>`, the shell in `<div id="app">`). Neither the skip affordance nor a main landmark to skip to is present. |
| BAR-280 | partial | Buttons and fields are announced with sensible names and correct native roles: native `<button>` with text labels, `<input>`/`<textarea>` associated by `<label for>` (`compose.rs`), and the native `disabled` attribute is set on busy/empty-disabled controls. But the like/follow toggles are plain `<button>`s whose on/off state is carried only by changing label text ("Like"/"Unlike", "Follow"/"Unfollow") with no `aria-pressed`, so no programmatic pressed/toggle state is exposed; `aria-busy` is never set during in-flight actions; and the "icon button" and "dialog" components the criterion lists do not exist in the build. Core name/role exposure is good; state exposure is incomplete. |
| BAR-281 | partial | A navigation landmark is exposed — `app.rs` renders the nav as a `<nav class="chirp-nav">`. But there is no `<main>` landmark on any screen (the required single main landmark is absent across landing, timeline, and the other views), no `<footer>` landmark on the signed-out shell, and no settings sub-section exists. One of the three required landmark types is present; the central main landmark and the footer landmark are missing. |
| BAR-282 | partial | Each view renders exactly one top-level `<h1>` that names the screen — "Timeline" (`timeline.rs`), "Compose"/"Log in to chirp" (`compose.rs`), the profile display name or a state title (`profile.rs`) — and the heading tree is flat with no skipped levels. But the browser tab title is the static `<title>chirp</title>` in the served shell and is never updated per route, so the top-level heading does not match the tab title as the criterion requires. Heading structure holds; title/heading correspondence does not. |
| BAR-283 | partial | The timeline feed is a navigable list — `timeline.rs` renders `<ul class="chirp-list">` with one keyed `<li>` per chirp, each a distinguishable item (author, text, meta) — and the "Load more" catch-up control is a named native `<button>`. But there is no "N new chirps" live catch-up affordance (no live insertion of new chirps), and the conversation, notifications, search-results, and followers/following list surfaces named by the criterion do not exist in the build (followers/following appear only as text counts on the profile card). | BAR-284 | partial | The product has no icon-only controls to mislabel — the compose affordance is a text nav link "Compose" and like/follow are text buttons — so icon labelling is not at risk. The current nav destination exposes **no** selected state at all: `nav_bar` in `app.rs` applies no `aria-current`, active class, or other indicator to the current link, so neither a programmatic nor a visual selected state is present. Like state is in the name; nav selected state is entirely absent. |
| BAR-286 | met | The layout is a single reading column that reflows naturally: the served stylesheet sets `body { max-width: 40rem; margin: 2rem auto }` with normal block flow, no multi-column layout, no fixed pixel widths or heights, and no `overflow:hidden` on text containers; the viewport meta permits zoom (no `maximum-scale`/`user-scalable=no`). A simple flowing single column at `max-width:40rem` reflows to one column below 320 CSS px without horizontal scrolling, zooms to 200% without clipping, and absorbs a text-spacing override without clipping or overlap. This visual check is settled from the complete served CSS and shell markup at `c805525` (the code artifact that determines it); a rendered zoom pass would confirm the structurally-guaranteed result. |
| BAR-287 | partial | A field error is carried by the text of a `role="alert"` banner (`compose.rs`), and an active like is carried by its label text ("Unlike"), so both are identifiable in greyscale or a colour-blindness simulation without relying on colour. But the current nav destination carries no non-colour indicator because it carries no indicator at all (no `aria-current`, no active class, no weight/underline difference in `app.rs`/CSS). Two of the three states are colour-independent; the current nav destination has no distinguishing treatment to begin with. |
| BAR-288 | met | No content in the product flashes. There is no CSS `animation`/`transition`/`@keyframes` and no JavaScript/WASM-driven flashing anywhere in `crates/chirp-frontend` or the served stylesheet; all content and state banners render statically. Nothing can flash more than three times per second. Settled from the absence of any flashing or animated content in the source at `c805525`. |
| BAR-289 | met | The product respects a reduce-motion preference because it contains no motion to reduce: there are no CSS transitions/animations/keyframes, menus/dialogs/toasts animate nothing (status and error banners appear instantly), the loading state is static text rather than a spinner, and no information is conveyed by movement. With no continuous or incidental animation anywhere in `crates/chirp-frontend` or the served CSS at `c805525`, a reduce-motion user encounters no unwanted motion. |
| BAR-290 | partial | Posting a chirp is announced through a polite live region: on success `compose.rs` renders the confirmation banner with `role="status"`, which a screen reader reports without moving focus off the user's control. But following an account produces no status announcement — `profile.rs` updates the follow button label and count on success with no polite live region (only the follow *error* uses `role="alert"`); there is no settings surface to save; and new-chirp arrival is not announced (the "Loading more…" indicator in `timeline.rs` is a plain `<p>` with no live region, and there is no automatic new-chirps insertion). One of the required status announcements is present; the others are absent. |
| BAR-291 | partial | The build has no sign-up flow — authentication is handle-based login (`compose.rs`), with no account creation and so no "taken handle" case. For the analogous login submission, a validation or server error is announced via a `role="alert"` banner (a forced submit failure is surfaced, not silent) and the message is plain words from `AppError::user_message` (`error.rs`), though a transport failure's text includes an HTTP status. However the field is not marked `aria-invalid`, and the error banner is not associated with the handle field via `aria-describedby`, so focusing the field does not re-read the error and the field is not programmatically reported invalid. Errors are announced; the field-invalid reporting, the re-read-on-focus behavior, and the sign-up scenario itself are absent. |
| BAR-292 | partial | A forced load failure is handled well: `timeline.rs` renders the error through a `role="alert"` banner with a reachable native "Retry"/"Try again" `<button>`, and the empty timeline shows an `<h1>Timeline</h1>` heading. But the loading state is not announced — "Loading timeline…" is a plain `<p class="chirp-loading">` with no live region, `aria-busy`, or hidden-skeleton handling; the empty state presents the heading but no next-step action (only "No chirps yet."); and acting with an expired session (a 401, observed live on `/api/timeline`) surfaces an error banner but neither routes to nor moves focus to a sign-in screen (no `.focus()` or redirect-on-expiry in `crates/chirp-frontend`). Failure announcement and retry are met; loading announcement, the empty-state next step, and expired-session focus handling are not. |
