# Responsive / typical-phone measurement — `manual_user_check` cluster

**Product measured:** `Nousix-LLC/nswe-demo`, chirp, reference commit `c805525`.

**Access note:** The deployed product was reached and exercised read-only: the served SPA shell, the
wasm-bindgen glue `/pkg/chirp.js`, and the wasm binary `/pkg/chirp_bg.wasm` were retrieved and inspected, and
the frontend source at `c805525` (`crates/chirp-frontend/`) was read to confirm what the wasm renders. A
rendered phone-viewport browser session was not driven (no browser was available to this measurement); it was
not needed, because the responsive behaviour of this product is fixed entirely by static artifacts — the
`<meta name="viewport">` in the served shell, the shell's inline CSS, the complete absence of any `@media`
rule or `.css` file, and the component tree in the frontend source — none of which varies by viewport. Every
verdict below is grounded in those served artifacts and the `c805525` source; where a surface the criterion
names does not exist in the product, that is recorded as observed, not assumed.

**Cluster facts that recur below (observed once, cited per row):** the served shell
(`crates/chirp-frontend/index.html`) carries `<meta name="viewport" content="width=device-width,
initial-scale=1">` and a single inline `<style>` — `body { max-width: 40rem; margin: 2rem auto; font-family:
system-ui }`, plus `.chirp-nav` and `.ferric-router-link`. There is no other stylesheet: the served
`chirp_bg.wasm` contains zero `@media` strings and sets no element styles, and the repository holds no `.css`
file. All `chirp-*` component classes are therefore unstyled, so every screen is default single-column block
flow inside a 40rem column that shrinks to the viewport on a narrow device. No `font-size` is set anywhere.
The persistent nav (`crates/chirp-frontend/src/app.rs`) is two links — `Timeline` and `Compose`. The route
table is `/` (timeline), `/compose` (login/compose), `/user/:id` (profile), and a not-found fallback.

## Verdict table

| bar_id | live_status | observation |
|--------|-------------|-------------|
| BAR-030 | partial | On a phone the surfaces that exist render without broken layout or unreachable controls: the timeline (`/`), compose and post (`/compose`), view a profile (`/user/:id`), and follow on a profile all sit in the single device-width column with no fixed-width element, so nothing clips or overflows. But the enumerated loop is not fully present: there is no reply control anywhere (compose always posts top-level, `reply_to: None`, per `crates/chirp-frontend/src/compose.rs`), and the timeline cards are display-only — author, text, a likes count, and a timestamp, with no like button on the card (`chirp_item` in `crates/chirp-frontend/src/timeline.rs`); the only like control is a "representative" one on the profile. A person on a phone cannot reply, and cannot like a chirp from the timeline, so the stated loop cannot be completed in full. |
| BAR-265 | partial | At a 360px-wide portrait viewport the layout holds: the single 40rem-max column shrinks to 360px, no element has a fixed width, so there is no horizontal page scroll, no control pushed off-screen, and the plain buttons/links are default-sized and tappable — opening and scrolling the timeline, opening Compose and posting, following then unfollowing on a profile (`set_follow` toggle in `crates/chirp-frontend/src/profile.rs`), and opening a public profile all work end to end. The loop is not complete, though: replying to a chirp and liking/unliking a chirp are not reachable (no reply affordance exists; the timeline exposes no like control — only a representative like control on the profile), so "the whole core loop end to end" cannot be walked at 360×640. |
| BAR-267 | missing | The navigation model the criterion describes does not exist at any viewport. The persistent nav (`crates/chirp-frontend/src/app.rs`, `nav_bar`) is exactly two links — `Timeline` and `Compose` — with no current-destination marking (no active class, no `aria-current`). There is no bottom tab bar at compact width and no persistent side navigation at wide width (the served wasm contains no `@media` rule and no viewport-conditional layout), and the destinations the criterion requires — Home, Explore, Notifications, Profile, Settings — have no routes and no entries. |
| BAR-268 | missing | There is no Landing screen: a signed-out visit to `/` shows the timeline directly, and the only sign-in surface is a handle field on `/compose`. No "Sign up" entry exists anywhere — the product has handle-only login (`render_login` in `crates/chirp-frontend/src/compose.rs`) and no account-creation path — and no "Sign in" entry is surfaced on any landing or public profile. Rules & terms and Help & support are absent from the whole product (no routes, no footer; the shell renders only the nav and the routed outlet). A signed-out public profile shows "Log in to follow"/"Log in to like" hints but none of the Sign up / Sign in / Rules & terms / Help & support surfaces the criterion requires. (Public timeline and profile are readable without a session, so there is no authentication wall — but the required join and support surfaces do not exist.) |
| BAR-269 | partial | Of the list screens the criterion enumerates, only the home timeline exists (there is no conversation view, notifications, search, followers, or following screen). On a compact viewport the home timeline keeps its load-older control reachable in the single column with no horizontal scroll — a "Load more" button, with "Loading more…" and "You're all caught up." end states (`footer` in `crates/chirp-frontend/src/timeline.rs`). The rest of the criterion is not met: there is no "N new chirps" catch-up control; the chirp cards expose no reply, like, or more controls (they are display-only); chirps are not links to a detail view, so there is no open-item-then-back interaction and no scroll-position restoration beyond the browser default. |
| BAR-270 | partial | The one authentication form that exists — handle login (`render_login`, `crates/chirp-frontend/src/compose.rs`) — follows the pattern the criterion asks for: a `<label for>` ("Handle") sits directly above its input, the "Log in" submit is the next element in the same single column (reachable by scrolling the form, never behind a side-by-side layout, no horizontal scroll), and a validation/server error renders inline as a `role="alert"` banner with the field, not in a summary elsewhere. The compose form behaves the same way. But four of the five forms the criterion enumerates do not exist in the product: there is no sign-up, no recover-access, no set-new-credential, and no edit-profile form, so most of the enumerated forms cannot be exercised. |
| BAR-271 | partial | On a compact viewport the public profile header renders most of its fields in the single column with no horizontal scroll (`loaded_view` in `crates/chirp-frontend/src/profile.rs`): display name, `@handle`, bio when present, and follower/following counts, with a Follow/Unfollow context action. Gaps against the criterion: there is no avatar in the header; one's own profile shows a "This is you." note with no "Edit profile" action; and there is no chirps list below the header — the profile endpoint returns no chirps, so a "representative" like control stands in place of the user's posts. The Settings hub and its sub-sections, which the criterion also requires as full screens with a labelled back, do not exist in the product at all. |
| BAR-272 | missing | The surface model this criterion describes is not present. Compose is a full page route (`/compose`), not a dismissible overlay or bottom sheet — its textarea and "Chirp" button are visible in the single column, but the browser back control navigates away from the page rather than dismissing an overlay onto an underlying screen. Report does not exist anywhere in the product. None of the destructive confirmations the criterion enumerates exist — there is no delete-account, delete-chirp, block, mute, end-session, or sign-out action, and therefore no confirm/cancel dialog to show without clipping. With Report absent, no overlay/sheet pattern, and no destructive confirmation present, the criterion as stated does not hold. |
| BAR-274 | met | The product reflows correctly to a phone viewport in both orientations. The served shell sets `<meta name="viewport" content="width=device-width, initial-scale=1">`, so the page uses the device width rather than a desktop fallback, and the layout is a single column whose only width rule is `max-width: 40rem` with no fixed-width element — so on a narrow device it shrinks to the viewport with no horizontal page scroll in portrait or landscape, and content reflows to the narrower dimension. Focusing the login handle input or the compose textarea triggers no browser auto-zoom: no `font-size` is set on any field (or anywhere), so the inputs use the default 16px, at or above the threshold below which mobile browsers zoom a focused field. No pinch-zoom is needed to read the default-size text in the reflowing column. This holds across the signed-in core-loop surfaces that exist (timeline, compose, profile). |
