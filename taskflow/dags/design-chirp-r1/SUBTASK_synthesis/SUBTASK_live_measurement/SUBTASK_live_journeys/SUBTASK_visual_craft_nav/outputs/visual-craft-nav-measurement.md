# Live measurement — navigation shell & visual craft (manual_user_check), cluster `SUBTASK_visual_craft_nav`

**Product measured**: `Nousix-LLC/nswe-demo`, chirp product at commit `c805525`.

**Access note.** The deployed chirp product was reached read-only and responds: the web root serves the SPA
shell and the health endpoint reports the `chirp-server` service healthy (version `0.1.0`). The live
deployment's synced revision is a few commits ahead of `c805525`, but the difference across that range is
confined to documentation, the `design/` tree, and deploy manifests — **no `crates/` (product) source
changes** — so the running frontend and backend are byte-identical to `c805525`, and the rendered product is
the `c805525` SPA. The UI is a Rust/WebAssembly single-page app (`crates/chirp-frontend`, `ferric` +
`ferric-router`); where a rendered judgement needed the exact markup, token, or type treatment, it was
confirmed against that SPA source at `c805525` (the running build carries no CSS or token files beyond the
small inline `<style>` in `crates/chirp-frontend/examples/index.html`, so the source is determinate for these
criteria). A single throwaway handle was used to reach the signed-in compose view. This cluster is the
`manual_user_check` navigation-shell / visual-craft partition; it judges only the 16 `BAR-*` assigned to it.

**Verdict table** (columns per the inherited `verdict_row_schema`: `bar_id, live_status, observation`; one row
per owned `BAR-*`; `live_status ∈ {met, partial, missing, not_applicable}`).

| bar_id | live_status | observation |
|--------|-------------|-------------|
| BAR-201 | missing | The persistent shell (`crates/chirp-frontend/src/app.rs` `nav_bar`) exposes only two destinations — "Timeline" and "Compose" — above a three-route table (`/` timeline, `/compose`, `/user/:id` profile, plus a not-found fallback). Of the six required shell destinations (Home, Explore, Notifications, Profile, Settings, Compose) only Home (as "Timeline") and Compose exist; Explore, Notifications, a Profile nav entry, and Settings have no route or nav affordance at all, so they are not reachable from any signed-in screen. |
| BAR-202 | partial | Each view renders an `<h1>` naming the screen ("Timeline", "Compose", "Profile", "Log in to chirp", "Not found"), so the main heading identifies the current screen. But the nav renders plain links (`ferric_router::link`, a `<span role="link">` with no active class — the `Link` builder's active-class option is unused in `nav_bar`), so the active primary-nav destination is not marked; and the browser tab title is the static `<title>chirp</title>` from `index.html` with no per-route update (no `document.title` write anywhere in the frontend), so the tab title never names the current screen. Two of the three where-am-I signals are absent. |
| BAR-204 | missing | Starting from the home timeline, Compose is reachable in one step via the nav. The other required destinations do not exist as routes: there is no own-profile nav entry (a profile is reachable only by typing `/user/:id`), and no Notifications, Settings, Explore, Help, or Rules route exists anywhere in the route table (`app.rs`). Most of the enumerated destinations cannot be reached in any number of steps. |
| BAR-208 | partial | Navigation uses the History API (`ferric-router` `navigate` → `history.pushState`, with a `popstate` listener syncing the reactive path), so the browser back control returns to the previous screen and re-renders it in place. Posting a chirp is a click-triggered async `POST` (`compose.rs` `submit_chirp` via `spawn_local`), not a form navigation, so pressing back after posting does not re-post. Two gaps: there is no scroll-position restoration (no scroll handling in the router or views), so a place in a scrolled timeline is not preserved on back; and the product renders no dialogs, so the "a dialog counts as one step / back dismisses it" behaviour cannot be exercised. |
| BAR-215 | partial | Across the three archetype screens (timeline `/`, profile `/user/:id`, compose `/compose`) the rendering is uniform because the product carries no custom CSS — body text is one browser-default size and leading on every screen, every control is a default `<button type="button">` of one shape, the one accent colour (`#1d9bf0` links) is applied identically everywhere, and no screen introduces a bespoke colour or control style. Consistency therefore holds, but by uniform browser defaults rather than a designed system: there is no designed primary-button colour (buttons are default grey) and no defined spacing rhythm, so the "buttons share one primary colour" treatment is not realised. |
| BAR-216 | partial | Body and reading text render at the browser default (16px ≥ 15px), and each screen's `<h1>` is the default larger, heavier heading, so the size floor and the heading-over-body hierarchy hold. Two parts fail: there is no type scale or line-height rule, so leading is the browser default (~1.2), not visibly generous; and meta text (the `chirp-meta` likes count and timestamp in `timeline.rs`) carries no styling, so timestamps and counts render at the same size and weight as body text rather than visibly quieter. |
| BAR-217 | partial | Contrast measured with a tool against the product's only colours (one shipped theme; no dark/alternate theme exists): body text black-on-white 21:1 (pass), default button text 18.3:1 (pass), and the default field-border `#767676` on white 4.54:1 (pass ≥3:1 for boundaries). The single accent colour `#1d9bf0` (nav and in-text links) measures 3.0:1 on white — it clears the 3:1 large-text/boundary bar but fails the 4.5:1 normal-text requirement, and links render at normal body size. The measurement passes for most samples but fails for normal-size link text. |
| BAR-219 | partial | On a wide window the reading column is held to a bounded measure: `index.html` sets `body { max-width: 40rem; margin: 2rem auto }`, so the timeline, conversation, profile, and forms are capped rather than spanning full width. On a phone viewport that same rule leaves `margin: … auto` resolving to zero horizontal space, so content meets the left and right edges with no consistent edge gutter. Item spacing is the browser default and uniform. The bounded-measure half holds; the phone edge-gutter half does not. |
| BAR-220 | missing | The product renders no menu, dialog, toast, or scrim: a search of the frontend finds no dialog/modal/overlay/scrim/toast/menu/popover element or styling (`crates/chirp-frontend/src`). The designed layering behaviour (menu above content, dialog above content on a dimmed scrim, toast above the dialog) has no surfaces to exist on; the stacking requirement cannot be satisfied because the layers are absent. |
| BAR-221 | missing | There are no icons anywhere in the UI — every control and nav entry is text (`nav_bar` renders "Timeline"/"Compose" as text links; like/follow/compose controls render text labels such as "Like", "Follow", "Chirp"). There is therefore no single icon set, no icon-only control needing an accessible name, and no icon fallback. The active primary-nav destination is not marked at all (plain links, see BAR-202), so it is not identifiable by any means, colour or otherwise, let alone in greyscale or a colour-blind simulation. |
| BAR-222 | missing | There are no menus, dialogs, or toasts to transition (see BAR-220), and the frontend contains no transition, animation, or reduce-motion handling of any kind. The "nothing animates continuously" condition is met only vacuously (there is no motion at all); the designed brief-transition-that-settles behaviour and the reduce-motion fallback do not exist. |
| BAR-223 | partial | Action-button copy across screens is sentence-case verbs, not "OK"/"Submit" or Title Case: "Log in", "Chirp", "Follow"/"Unfollow", "Retry", "Load more", "Try again". A forced form error shows a plain-language message with a way forward and no stack text: an invalid entry surfaces the validation rule ("text must not be empty", "username must not be empty") and a failed submit surfaces the server error's plain message, both in a `role="alert"` banner at the form with the control re-enabled for retry. One gap: the error funnel's transport-fallback path (`error.rs` `user_message`) renders "Something went wrong: HTTP status {code} … for {url}", which exposes a raw HTTP status code and an internal `/api/...` path on a non-decodable server or transport failure. Copy and the primary error path are met; the no-raw-code requirement is not uniformly held. |
| BAR-224 | missing | The product has no token set, no library components, and no themes. Every surface is raw HTML elements with browser defaults (chirp rows, buttons, text fields, and error `<p role="alert">` banners are hand-built in the feature modules; no shared component library, no `contracts`/token file, no CSS). There are no token roles to match (no defined primary or danger colour — a "destructive" action has no distinct treatment), no type scale, and no dialog to inspect. The shared-treatment-against-a-token-set requirement has nothing to measure against. |
| BAR-225 | partial | Of the compose/card behaviours, only part is present. An empty draft keeps Post disabled and posts nothing (`compose_submit_enabled` requires non-empty), and a valid chirp posts and is confirmed. But there is no character counter at all — the textarea relies on `maxlength="280"` to block overflow, so there is no counter to turn to a danger treatment. A posted chirp is confirmed by a "Chirped!" banner, not rendered as a card in compose; and the timeline chirp row (`timeline.rs` `chirp_item`) shows the author as a numeric user id, the body text, a plain "N likes" count, and a raw-milliseconds timestamp — no avatar, no handle, no relative time, and no like/reply/more-actions row. The like control (on the profile, `profile.rs`) is a text button reading "Like"/"Unlike (N)" — no filled icon and no "Liked" label. Most of the designed card and counter treatment is absent. |
| BAR-227 | missing | The product has no sign-up flow. The `/compose` route's logged-out state (`compose.rs`) is a handle-based *login*, not an account sign-up: it validates handle format (`Username::parse`, surfacing a plain field-level rule such as "username must not be empty" or an invalid-character error) but performs no handle-availability check, shows no "handle already in use" error, and has no pending/checking state while an availability lookup runs. The sign-up handle-availability treatment the criterion describes does not exist. |
| BAR-229 | partial | The compose/post path meets the criterion: publishing shows a brief non-blocking "Chirped!" confirmation (`role="status"`), the in-flight control shows a busy, disabled, non-re-triggerable state ("Chirping…"), and a forced in-place failure shows the error at the control with the control re-enabled to retry while the drafted text is kept (uncontrolled input, not cleared on error). The other named actions are weaker: following an account (`profile.rs`) shows a busy state and an inline failure with retry but gives no explicit confirmation — only the follower count and button label change; and "saving a setting" has no surface because no settings screen exists. |
