# Core-loop measurement — `manual_user_check` cluster

**Product measured:** `Nousix-LLC/nswe-demo`, the deployed `chirp` product at commit `c805525`.

**Access note.** The running product was reached and exercised live over its one web address: the single-page app, the `/healthz` probe, and the `/api/*` REST surface all answered, and the built WASM bundle (`/pkg/chirp.js`, `/pkg/chirp_bg.wasm`) is served, so the frontend runs. The data behaviors below were judged by exercising the API end to end with two throwaway test accounts (read-only beyond those accounts' own ordinary actions). The UI-presentation behaviors were judged against the `c805525` frontend source compiled into the served bundle (`crates/chirp-frontend/src/{app,timeline,compose,profile}.rs`) and the server routing (`crates/chirp-server/src/api/router.rs`), which is where the running SPA's screen inventory and affordances can be read off a code artifact; the running SPA cannot be clicked headlessly here. No credential-based sign-up exists in this build — authentication is handle-only — so account-model criteria were exercised through the create-user and session endpoints.

The `design` methodology loader was unavailable run-wide (`agent_domain_unset`); this cluster applied the principal-product-designer persona and the relayed ReleaseBar guidance and proceeded, as every gate node did.

Verdict rows conform to the inherited `verdict_row_schema` (`bar_id, live_status, observation`); `live_status ∈ {met, partial, missing, not_applicable}`.

| bar_id | live_status | observation |
|--------|-------------|-------------|
| BAR-100 | met | Registering a person returns exactly one `User` carrying an opaque `id`, `username`, `displayName`, an optional `bio` (created A with `bio` absent → `null`; created B with `bio:"hi i am b"` → present, so absent and empty are distinguishable), a `createdAt` epoch-ms, and `followerCount`/`followingCount`. There is a single `User` entity: `GET /api/users/{id}` returns it as the public profile and `POST /api/sessions` returns the same shape as the account its holder manages; no second "profile" entity exists. |
| BAR-101 | met | `POST /api/users` accepted a valid handle (`probe_a_205129`); a duplicate handle returned `409 CONFLICT` naming the handle; a handle with a space returned `400 VALIDATION_ERROR` ("username contains a disallowed character: ' '"); a 16-character handle returned `400 VALIDATION_ERROR` ("username is 16 characters but at most 15 are allowed"). Handle rule (1–15 ASCII letters/digits/underscore) and uniqueness hold, so at most one account holds any handle. Note: the structured validation `details.field` is reported as `"body"` rather than `"username"`, with the handle-specific reason in the message — the refusal and its reason are clear, but not routed to a named handle field at the API. |
| BAR-102 | met | Account and chirp ids are server-assigned opaque integers from monotonic counters; `CreateUserRequest`/`CreateChirpRequest` carry no id field. A create-user request with an extra `"id":999999` was accepted and the server still assigned its own id (`48`), so no create surface honors a client-supplied id. Clients only echo back ids the product issued. |
| BAR-104 | met | Every account and chirp returned a `createdAt` in epoch-milliseconds; three accounts created in sequence carried strictly increasing `createdAt` (…889368, …889470, …889914), matching creation order, and chirps likewise. No surface mutates `createdAt` (there is no update endpoint). Ordering is comparable for the newest-first timeline (the store orders newest-first by monotonic id, a stable proxy, with timestamps recorded on each entity). |
| BAR-105 | missing | There is no way for a holder to change their display name or bio. The server exposes no profile-edit route (`PUT`, `PATCH`, and `POST` to `/api/users/{id}` each returned `405`, and the display name was unchanged afterward), and the frontend has no edit-profile surface (`crates/chirp-frontend` has only timeline, compose, and profile views, none of which edits the account). The criterion's secondary clause — no surface changes an account's id or creation time — holds only because no mutation surface exists at all. |
| BAR-106 | met | `POST /api/chirps` as the authenticated caller returned a chirp with an `id`, the caller as `authorId`, the body as written, a `createdAt`, `likeCount:0`, and `replyTo:null`. An empty body returned `400` and a 281-character body returned `400` ("at most 280 are allowed"); a 280-character body was accepted (`201`). No update-chirp surface exists, so body and author are immutable after posting. |
| BAR-107 | met | A reply posted with `replyTo` set to an existing chirp (`9`) recorded that target (`replyTo:9`); a reply to a non-existent chirp id (`999999`) was refused `404 NOT_FOUND` ("reply target chirp-999999") and created nothing, so no reply carries a dangling target. |
| BAR-108 | met | A self-follow was refused `403 FORBIDDEN` ("a user cannot follow themselves"). `PUT /api/users/{id}/follow` from A to B returned `following:true, followerCount:1`; a second identical follow left the count at `1` (idempotent). `DELETE` unfollowed, and on the next timeline read B's chirps had left A's timeline (the follow edge was removed). Following a non-existent user returned `404`. |
| BAR-109 | met | After A followed B, B's `followerCount` read `1` and A's `followingCount` read `1`; after A unfollowed, both returned to `0`. One follow moved each count by exactly one; the idempotent repeat did not move them. |
| BAR-110 | met | Liking B's chirp returned `liked:true, likeCount:1`; liking it again left `likeCount:1` (idempotent, no second like). Unliking returned `likeCount:0`; unliking again stayed at `0` with no underflow. Liking a non-existent chirp returned `404`. The count equals the number of distinct accounts that currently like the chirp and moves by one on a genuine like/unlike. |
| BAR-111 | met | A's home timeline returned A's own chirps plus followed B's chirp and no unfollowed account's chirps, newest-first. `GET /api/timeline?limit=2` returned a bounded first page with `nextCursor`; passing that cursor returned the strictly-older next page; `limit=100000` was clamped (returned all 5, not an error), so a client cannot force the whole history into one response. After A unfollowed B, B's chirp left the next timeline read with no stale materialized timeline, so the timeline is derived. |
| BAR-117 | met | Every relationship-creating surface validates its referenced entities against the live store: posting checks the author exists and, for a reply, that the target chirp exists (else `404`); follow/unfollow and like/unlike each return `404` for a non-existent target. No surface produced a chirp, reply, follow, or like naming a non-existent entity. |
| BAR-163 | met | Against the running product, domain-invariant violations are refused with a machine-readable category and store nothing: a self-follow returned `403 FORBIDDEN`; liking an already-liked chirp was idempotent (count stayed `1`, no second like stored); a forged/invalid bearer token returned `401 UNAUTHORIZED`, and the server (not the client) resolves the authenticated author so a chirp cannot be attributed to a non-existent account (`crates/chirp-server` checks author existence in `create_chirp`). Error categories observed: `VALIDATION_ERROR`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`. |
| BAR-209 | partial | The timeline (`crates/chirp-frontend/src/timeline.rs`) loads a bounded first page (requests 20; the server clamps and returns a cursor) and offers an explicit "Load more" control that appends the next cursor page, with a "You're all caught up." end note. But there is no way to pull in chirps posted since the list was opened — no catch-up / "N new chirps" / refresh affordance exists. Two of the three required behaviors are present; the pull-in-new behavior is absent. |
| BAR-211 | partial | Posting a chirp shows a non-blocking success banner ("Chirped! (id)", `role="status"`) and failures show an inline error (`role="alert"`) at the compose control, with the draft preserved; login and timeline-load failures likewise show inline errors with retry. However, follow and like actions on the profile show only a busy state and an error-on-failure — a successful follow/like is not confirmed beyond the label/count flipping — and action classes such as "saving a setting" do not exist in this build. Completed-action confirmation is present for composing but not uniformly for the other core-loop actions. |
| BAR-212 | partial | A persistent nav "Compose" affordance is rendered above every route (`crates/chirp-frontend/src/app.rs` `nav_bar`), so it is reachable from the timeline and a profile, and the dedicated `/compose` URL opens the compose surface directly. But the affordance navigates to a separate `/compose` screen rather than letting a person start composing in place without leaving the current screen, and there is no Notifications screen among the enumerated vantage points (the shell has only Timeline and Compose). |
| BAR-238 | partial | Opening the home destination shows a timeline of the viewer's own chirps and those they follow, newest-first (grounded live), arriving as a bounded first page with a visible "Load more" that brings a further bounded page, and never loading the whole timeline at once; following an account that had posted interleaves its chirps newest-first. The failing clause is the shell: the destination is labelled "Timeline" (not "Home") and the two-link nav marks no active/current destination, so the shell does not mark Home as current. |
| BAR-239 | missing | There is no catch-up control: the timeline has no "N new chirps" affordance and no way to jump back to the newest chirps as a single bounded step. There is also no chirp conversation screen in this build (routes are only `/`, `/compose`, `/user/:id`), so opening a conversation and returning with scroll position preserved cannot occur. |
| BAR-242 | missing | The compose surface exists in only one placement — the `/compose` screen (`crates/chirp-frontend/src/compose.rs`). There is no inline composer at the top of the timeline, no Compose dialog opened from the shell, and no reply composer in a conversation (no conversation screen exists). The one composer shows a placeholder and disables its action while empty, but has no live remaining-character count (only a `maxlength` attribute), and its action is labelled "Chirp" in every case, never "Post"/"Reply". The three-placement, consistent-behavior, counted, Post/Reply-labelled requirement is not met. |
| BAR-243 | missing | A reply cannot be composed through the UI at all: the compose form hardcodes `reply_to: None` (`validate_chirp` in `crates/chirp-frontend/src/compose.rs`), and there is no chirp conversation screen with a reply control. The API supports replies (grounded via BAR-107), but the running product exposes no reply affordance and no conversation view, signed-in or signed-out. |
| BAR-244 | missing | There is no genuine like control on chirps. The timeline renders each chirp as author id, body, a static "{n} likes" count, and a raw "{ms} ms" timestamp — with no like affordance. There is no conversation screen. The only like control is an explicit "representative" stub on the profile (`like_control` in `crates/chirp-frontend/src/profile.rs`), not attached to any displayed chirp, labelled "Like (n)"/"Unlike (n)" with a note reading "Representative like control for this profile" — it carries no filled-heart / "Liked" more-than-colour treatment and is not the per-chirp control the criterion describes, nor consistent across timeline/conversation/profile. |
| BAR-245 | partial | The profile carries a working follow/unfollow control (`crates/chirp-frontend/src/profile.rs`): it toggles and reflects the server's idempotent follow state and follower count, shows a busy "Working…" state, and surfaces failures in an error banner at the control. But its followed-state label reads "Unfollow" rather than "Following"; a viewer's own profile shows a plain "This is you." note rather than an "Edit profile" entry (no edit-profile surface exists); and there are no person rows (no followers/following lists), so the "same wherever it appears" requirement across placements cannot hold. |
| BAR-246 | partial | The profile route is `/user/:id` (a numeric id, not the handle URL the criterion names). It shows the display name, `@handle`, bio (when present), and follower/following counts, and loads both without a session and with one (`GET /api/users/{id}` is unauthenticated, returned `200`); signed in, the header carries the follow control. The failing clauses are substantial: there is no avatar, the person's own chirps are not shown at all (the server has no per-user chirps endpoint, so the profile lists none), the address is id-based not handle-based, and the owner's own profile shows "This is you." rather than an "Edit profile" entry. |
| BAR-247 | missing | A profile's follower and following counts are static text (`<strong>n</strong> followers` / `following`), not links, and there are no followers or following list screens — no routes for them and no server endpoints to enumerate a user's followers or followees. Neither list, nor its own URL, nor per-row person entries with a follow control exist. |

## Summary (not part of the schema)

- **met (12):** BAR-100, 101, 102, 104, 106, 107, 108, 109, 110, 111, 117, 163 — the whole backend core loop (account model, handle rules, opaque ids, timestamps, compose/post, reply targeting, follow, like, counts, derived newest-first paginated timeline, referential integrity, server-enforced invariants) is present and correct on the live product.
- **partial (6):** BAR-209, 211, 212, 238, 245, 246 — the surface exists and the core behavior works, but a named element is absent (pull-in-new; uniform action confirmation; in-place/Notifications compose; Home shell marking; "Following" label + Edit-profile + person rows; avatar + own-chirps list + handle URL + Edit-profile).
- **missing (6):** BAR-105, 239, 242, 243, 244, 247 — no profile editing, no catch-up/conversation, a single bare composer (no dialog/inline/reply, no counter, "Chirp"-only label), no UI reply path, no real per-chirp like control, and no followers/following lists.
- **not_applicable (0).**
