## Concern-coverage note (concern 4)

- **Gating** — *clean.* `needs: [fmt, clippy, test, wasm, doc]` publishes only after all five checks pass; `if: github.event_name == 'push' && github.ref == 'refs/heads/main'` correctly scopes the job to `main` pushes only (PRs get `pull_request` event → skipped), so `image` is correctly **not** a PR required check. `concurrency.cancel-in-progress` is `false` for `main` (`github.ref != 'refs/heads/main'` ⇒ false on main), so an in-flight publish is never cancelled. The only gating caveat is the `workflow_dispatch` exclusion (IMG-3, nit).
- **Skip-detection logic** — *correct-but-now-dead (IMG-2, minor).* With `./Dockerfile` present on `main`, the detect step always reports `present=true`; the skip (`else`) branch is dead and does not misfire (correct working directory, correct repo-root path). The only residual concern is the latent silent-skip-on-removal hazard, recorded as IMG-2.
- **Build context & Dockerfile path** — *clean.* `context: .` = repo root = `$GITHUB_WORKSPACE`; `file: ./Dockerfile` resolves to the real repo-root Dockerfile. `setup-buildx-action@v3` + `build-push-action@v6` give BuildKit, so the Dockerfile's `# syntax=docker/dockerfile:1` and `--mount=type=cache` features work. `.dockerignore` (verified at `61f924a`) correctly trims `target/`, `.git/`, `.github/`, docs — and the image job does no `cargo build` on the runner, so `target/` is absent from the fresh checkout regardless; context is clean. `deploy/docker/healthcheck.rs` (referenced by the Dockerfile) is present at `61f924a`.
- **Image name/tag** — *clean.* `IMAGE_NAME: ghcr.io/nousix-llc/chirp-server` correctly lowercases the `Nousix-LLC` owner (GHCR requires a lowercase path). `docker/metadata-action@v5` emits `type=sha,format=long` (full-SHA, traceable) and `type=raw,value=latest`. `REGISTRY` (`ghcr.io`, used by the login step) and the fully-qualified `IMAGE_NAME` (used by metadata-action) are consistent with no double-prefix. Tagging `latest` on each `main` push is a conventional, acceptable choice (deployment *targeting* of `latest` is out of scope and not done here).
- **GHCR auth (functional)** — *clean.* Job-level `permissions: { contents: read, packages: write }` grants `GITHUB_TOKEN` the `packages:write` needed to push to GHCR; `docker/login-action@v3` logs in with `username: github.actor` / `password: secrets.GITHUB_TOKEN` (standard, no PAT/secret). First-publish will create the org package under `nousix-llc` via the token — a one-time operational linkage, not a workflow defect. (The *security scoping* of `packages: write` is `SUBTASK_supply_chain_security`'s call, not restated here.)
- **Digest / push correctness** — *clean, minor traceability gap.* `push: true` with meta-derived `tags`/`labels` publishes both the long-SHA and `latest` tags; `cache-from/to: type=gha` is valid with buildx and independent of the `permissions:` block (GHA cache uses its own runtime token). No digest is surfaced for provenance (IMG-4, nit).
